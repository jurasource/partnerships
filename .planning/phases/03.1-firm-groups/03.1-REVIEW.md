# Phase 03.1: Code Review Report

**Reviewed:** 2026-06-15T00:00:00Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed the firm-groups feature across the data layer (schema, server actions, types), two new pages (`/groups`, `/groups/[id]`), updates to the firms page and table, and supporting UI components. The server actions are well-structured with Zod validation, appropriate cascade FK behaviour, and good error handling patterns. The test suite covers the happy paths and key guard clauses.

Four warnings require attention before shipping:

1. **Stale UI after create/delete in `GroupFormDialog` and `GroupsTable`** — the most user-visible defect. Two client components invoke server actions that call `revalidatePath` but never trigger a client-side router refresh, so the UI does not update until the user navigates away and back.
2. **No `UNIQUE` constraint on `groups.name`** — duplicate group names are silently allowed at the DB level.
3. **`capabilityTags` filter bar uses a hardcoded static list** — any capability tags added by users beyond the three seed values will never appear in the filter dropdown.
4. **`updateGroup` does not revalidate the group detail path** — after a rename the `/groups` list is invalidated but `/groups/[id]` is not, creating a potential stale-page scenario in cached deployments.

## Warnings

### WR-01: GroupFormDialog — no router.refresh() after successful create; new group not shown until navigation

**File:** `src/components/groups/group-form-dialog.tsx:58-62`

**Issue:** On a successful `createGroup` call the dialog closes with `setOpen(false)` and `resetForm()` but never calls `router.refresh()`. The server action does call `revalidatePath("/groups")`, but in a `force-dynamic` RSC page that revalidation is only acted upon by the Next.js router when a navigation occurs. In the current flow the user sees the same (stale) groups list after dismissing the dialog — the newly created group is invisible until they navigate away and return.

The same pattern is correctly handled in `GroupDetailClient` (lines 53 and 90) which calls `router.refresh()` after every mutation; `GroupFormDialog` diverges without justification.

**Fix:**
```tsx
// Add to imports
import { useRouter } from "next/navigation";

// Inside GroupFormDialog component body
const router = useRouter();

// Replace the success block (line 58–62) with:
if (result.ok) {
  toast.success("Group created");
  setOpen(false);
  resetForm();
  router.refresh();   // <-- pull the updated RSC data
}
```

### WR-02: GroupsTable — no router.refresh() after successful delete; deleted row remains visible

**File:** `src/components/groups/groups-table.tsx:49-58`

**Issue:** `GroupRowActions.handleDelete` calls `deleteGroup` and shows a toast on success but never calls `router.refresh()`. The component is `"use client"` with no router import. The server action invalidates `/groups` via `revalidatePath`, but that only takes effect when the Next.js router re-fetches. The deleted row remains in the table until the user manually navigates away.

**Fix:**
```tsx
// Add to imports at top of file
import { useRouter } from "next/navigation";

// Inside GroupRowActions component body
const router = useRouter();

// After toast.success (line 55):
if (result.ok) {
  toast.success(`"${group.name}" deleted`);
  router.refresh();   // <-- pull the updated RSC data
}
```

### WR-03: groups.name has no UNIQUE constraint — duplicate group names silently permitted

**File:** `src/db/schema.ts:158-165`

**Issue:** The `groups` table has no `uniqueIndex` on the `name` column. Two groups named "Nuclear Consortium" can be created; both appear in the dropdown and filter bar with no way for the user to distinguish them. This also defeats the UI expectation of a unique human-readable label per group. Every other dedup-sensitive column in this schema (OCDS `ocid`, `findings` `(firm_id, topic_id)`) has an explicit unique constraint; `groups.name` is the exception without explanation.

**Fix:**
```ts
// In src/db/schema.ts, change the groups table definition to:
export const groups = pgTable(
  "groups",
  {
    id: text("id").primaryKey().$defaultFn(() => crypto.randomUUID()),
    name: text("name").notNull(),
    createdAt: timestamp("created_at", { mode: "string" }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { mode: "string" }).notNull().defaultNow(),
  },
  (table) => [uniqueIndex("groups_name_unique").on(table.name)],
);
```

Then run `npm run db:push`. Also update `createGroup` and `updateGroup` in `group-actions.ts` to catch the unique-constraint violation and return a user-facing error (e.g. `"A group with that name already exists."`).

### WR-04: updateGroup does not revalidate the specific group detail path

**File:** `src/lib/actions/group-actions.ts:78`

**Issue:** `updateGroup` calls `revalidatePath("/groups")` but not `revalidatePath("/groups/${id}", "page")`. When deployed with any caching layer (ISR, CDN, future Vercel deployment), the detail page at `/groups/[id]` continues to serve the old name after a rename until the cache entry for that specific path expires. The client-side `router.refresh()` in `GroupDetailClient` corrects the in-session view but does not purge the server cache for other visitors or new sessions.

Note: `deleteGroup` (line 99–100) and membership mutations (lines 125–126, 149–150) correctly call `revalidatePath("/firms")` in addition to `/groups`, but none of them invalidate `/groups/[id]`.

**Fix:**
```ts
// In updateGroup, replace line 78:
revalidatePath("/groups");
revalidatePath(`/groups/${id}`, "page");  // invalidate the detail cache

// Optionally apply the same pattern to addFirmToGroup and removeFirmFromGroup:
revalidatePath(`/groups/${groupId}`, "page");
```

### IN-01: ALL_CAPABILITIES is a hardcoded static array — user-added capability tags cannot be filtered

**File:** `src/components/firms/firms-table.tsx:256`

**Issue:** The capabilities filter dropdown is populated from the module-level constant `ALL_CAPABILITIES = ["Nuclear", "Infrastructure", "Consultancy"]`. The CLAUDE.md spec explicitly describes capability tags as "data-driven (never hard-coded enum column)" with the note that "users can extend via the config UI." If a user assigns a tag not in these three (either directly in the DB or via a future config UI), it will never appear as a filterable option in the dropdown, silently omitting it from the filter surface while still appearing as a badge on rows.

**Fix:** Derive `allCapabilities` from the actual data rather than the static constant. In `FirmsTable`, replace:
```ts
// Remove
const ALL_CAPABILITIES: string[] = ["Nuclear", "Infrastructure", "Consultancy"];

// Add inside FirmsTable, alongside allGroups useMemo:
const allCapabilities = React.useMemo(() => {
  const seen = new Set<string>();
  for (const firm of data) {
    try {
      const tags = JSON.parse(firm.capabilityTags as string) as string[];
      for (const t of tags) seen.add(t);
    } catch { /* ignore */ }
  }
  return Array.from(seen).sort();
}, [data]);
```
Pass `allCapabilities` to `FirmsFilterBar` in place of the constant.

### IN-02: capabilityTags parsed twice per-filter-pass — consider deriving parsed tags once

**File:** `src/components/firms/firms-table.tsx:157-160` and `298-302`

**Issue:** `capabilityTags` is JSON-parsed in two separate places: once in the TanStack `accessorFn` for display, and again inside the `filteredData` useMemo for filtering. For a large dataset this doubles the parse work per re-render. The field is typed as `string` from Drizzle (because the column is `text`) and the `as string` cast on line 158 and 300 suppresses any future type-checking if the field type changes.

**Fix:** Pre-parse into a derived field when building `firmsWithGroups` in the RSC (`firms/page.tsx`), or extend the `FirmWithGroups` type to include `parsedCapabilityTags: string[]` computed once in a `useMemo` inside `FirmsTable`. Either approach eliminates the double-parse and removes the `as string` cast.

### IN-03: Select onValueChange type annotation is incorrect in group-detail-client.tsx

**File:** `src/components/groups/group-detail-client.tsx:196`

**Issue:** The `onValueChange` callback is annotated as `(value: string | null) => void`, but shadcn/ui's `Select` component types `onValueChange` as `(value: string) => void` — it never emits `null`. The `value ?? "all"` guard on the same line in `firms-filter-bar.tsx:153` reflects the same confusion. The annotation is harmless at runtime but is misleading and may produce a TypeScript type error depending on the component library version.

**Fix:**
```tsx
// Change line 196 from:
onValueChange={(value: string | null) => { if (value) handleAddFirm(value); }}
// To:
onValueChange={(value: string) => { if (value) handleAddFirm(value); }}
```
